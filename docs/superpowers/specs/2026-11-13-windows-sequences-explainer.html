Intro

What a window is, and why sequences need one

A window is a named span of fight time the priority can read: window.W.up, when it expires, and for a sequence which step is due next. The core rebuilds its picture from scratch on every update and keeps nothing between updates, so anything that must be remembered across updates (a sequence is at step 2, a burst window opened 3 s ago) has to live in the belief. Today a strict sequence is approximated with prev.1 chains; the design turns every sequence into a window with steps, advanced by the casts the belief observes.

Lua-led window

Declared in the class file with spec:RegisterWindow. Its evaluator is a function the belief runs every Drain, with edge rules: a rise opens, a fall closes only with close_on_false. One shared instance. A window with steps must have an evaluator: nothing opens on a cast of a first step. New in 0.9: an optional reset_on_target_change field. Hunter weave and Rogue riposte stay this kind.

APL-led window

Declared in the priority: in the windows list, or by a sequence / strict_sequence line. It has no evaluator. Its lines are commands: the display's pass at time = now runs them in list order and sends the belief the operations that changed the window. The belief replays them. One window per display, each under its own key.

Level, not edge

Nothing remembers an APL line's previous value. A condition that stays true keeps the window open and reopens it after it expires. A line that is not reached does nothing. A bare open_window reached every pass is a window that is always open.

No guardrails

The owner's ruling: "the signal that is sent should just follow the APL instead of collecting and applying boolean logic. These are tools for APL pack authors and don't need guardrails against bad APL design." A priority that opens and closes a window every pass is allowed; the snapshot shows it.

What changed since v5. The machinery in the diagrams is the same. The last ten questions and eight derived rules were answered.
  • The plain-sequence option is mode=skip|wait|continue. wait_on_ready=1 is an alias for mode=wait with SimC's exact meaning; the translator writes mode=continue.
  • No restart cap. The fired mark resets per slot, so forecasts show windows opening and closing.
  • Open and close lines carry only name= and if= for every window, class windows included.
  • The step deadline is 4 s with a step_timeout= option. A sequence that begins with a cooldown starts in Primary and AOE.
  • reset_on_target_change exists for Lua windows too. Hunter hha and Paladin move1 / move2 become APL sequences in Phase 3.

Rules at a glance

Twenty-three rules, as v6 states them

  1. Every window's state lives in the belief. The core keeps nothing between updates.
  2. A window is declared in one of three places: in the class file (Lua, with an evaluator), in the priority's windows list, or by a sequence / strict_sequence line, which declares its own. windows is a reserved list name.
  3. A window used by open_window or close_window must be declared exactly once. An undeclared name, a second declaration, or a declared name the class already registers in Lua is a compile error.
  4. Changed. open_window and close_window lines carry only name= and if=, for every window, Lua-registered ones included. Settings live only in the declaration. The name may be a sequence's.
  5. APL window lines are commands, run in list order. A true open_window opens the window; if it is already open nothing happens, unless it is declared refresh=1. A true close_window closes it.
  6. There are no edges for APL windows. A condition that stays true keeps the window open, and reopens it after it expires. A line that is not reached does nothing.
  7. Changed. After a line changes the window, the walk starts again from the top with time unchanged. Each line can act once per slot: the fired mark is cleared at the start of every slot. There is no restart cap; restarts per slot cannot exceed the number of window lines.
  8. Only slot 1's walk at time = now talks to the belief. It sends the ordered list of operations that changed the window. The belief replays them, in order, at the start of its next update, as writes. Forecast slots act on the copy and never send.
  9. Each display has its own copy of every APL window, under its own key (<pack>:<name>#<display>). The belief knows nothing about displays or priority lines. Lua windows are one shared instance.
  10. Changed. Lua windows keep their evaluator and edge rules. New: the optional field reset_on_target_change, default off.
  11. A press never opens a window. Presses (observed casts) advance the steps of a sequence that is already open.
  12. A strict sequence opens when its line is the one chosen at now. By default (SimC) it can be chosen only when every member can be cast now, with no tolerance; with start_on_first=1 (wowsims) when its first member is due within the spell queue window. While open, that display shows no on-GCD line outside it; use_off_gcd=1 lines are still shown unless the sequence says hold_off_gcd=1. A step not pressed within step_timeout (4 s) closes it.
  13. Changed. A plain sequence opens when its line is reached at now and its condition is true. mode= says what happens when the due member cannot be cast: skip (default) drops it for this run; wait shows it with its countdown and recommends nothing below; continue stays on it and lets the list carry on. A line whose if= is false shows and skips nothing.
  14. After its last step a plain sequence parks: up, no step due, until restart_sequence or combat end. window.<seq>.done is true while parked. A loop is restart_sequence,name=x,if=window.x.done.
  15. "Can be cast" is judged at the moment the player can next act: the end of the GCD or cast for an on-GCD member, now for an off-GCD one.
  16. Sequence behaviour is written on the line. What a line does not say is SimC's behaviour. Option names are SimC's where SimC has one and SimC-styled where it has none. An import adds nothing. The wowsims translator writes the wowsims settings on every sequence it emits. An option an entry does not take is a compile error.
  17. A window also closes at its duration, at max_duration, at combat end, on a closeWindow from a real cast, and (strict) on any other on-GCD cast or at the step deadline. A target change closes nothing unless the declaration says reset_on_target_change.
  18. Changed. While a sequence's window is up in a display, that display shows its members even when it would normally filter them out. In Primary and AOE the start line also skips the "toggle shown separately" test, so a sequence that begins with a separated cooldown starts there. A switched-off toggle still disables the member.
  19. Primary and AOE each have a "Sequences" setting, on by default. Where it is off, sequences do not exist for that display. Cooldowns, Interrupts and Defensives never sequence. Free-form windows work in every display.
  20. An unnamed plain sequence is default, as in SimC; further unnamed sequences and every unnamed strict one get generated names.
  21. These are tools for pack authors. The engine does not protect against a priority that opens and closes a window every pass; the snapshot shows it, with the restarts per slot.
  22. Every parameter of a sequence line, a windows declaration and an open or close line is visible and editable on the Actions tab, shown with its effective value, defaults included.
  23. New. A step is a cast; moves and waits are never steps. In the default strict start test a member after the first may be judged with some of its gates skipped (sequence_ignore) or by its own handler (sequence_ready), both declared by the pack on the ability. That is how a sequence whose first member enables its second can start without start_on_first=1.
Declarations

The windows list, and what fails to compile

Anonymous windows are declared once in a named list, as precombat is a named list. The list is read at compile time only: it is never walked and cannot be called. SimC imports simply lack it; sequences declare their own window.

Declare, then use

actions.windows+=/window,name=burst,duration=12 actions.windows+=/window,name=pool,duration=6, refresh=1,max_refresh=2,max_duration=15 actions+=/open_window,name=burst,if=cooldowns_up actions+=/close_window,name=burst,if=target.dying

  • name and duration (seconds, or combat) are required.
  • refresh, max_duration, max_refresh are optional and mean what they mean for a Lua window. reset_on_target_change=1 is optional too: a target change then closes the window.
  • "Before use" means the compiler reads this list before every other list (text order is lost once lists are stored by name).
  • windows is a reserved list name. A user's old ordinary list of that name gets E5; the release notes say so.
  • Lines that name a Lua (class) window have the same form: name= and if= only. They act on the forecast and send nothing; the length comes from RegisterWindow.
ErrorWhen
E1An open_window / close_window names a window that is not in the list, not a sequence of this priority and not a class window.
E2A name declared twice: two list entries, two sequences, or one of each.
E3A declared name that a class already registers in Lua, in any spec.
E4An open or close line that carries anything besides name= and if=, whatever kind of window it names.
E5A window entry outside the list, any other entry inside it, if= on an entry, or the list being called.
E6A missing or non-positive duration, bad caps, or a non-positive step_timeout.
E7An option the entry does not take: anything outside the option table on a sequence or window entry, v4's four names included; a bad mode= value; mode= with wait_on_ready.

An error disables the offending line, is listed with the priority's warnings, and fails the build for shipped packs.

Ability fields for the strict start test

SimC's start rule, every member castable now, cannot pass when the first member enables a later one: battle_stance:overpower out of Battle Stance. Two optional fields on the ability, written by the pack, tell the start test how to judge such a member. The core knows four kinds of gate, which are fields it already reads; it knows no stance by name.

Paladin Retribution: move1 / move2

actions.move_to_melee=sequence,name=move1,mode=continue,if=<cond>&<before first swing>&!window.move1.done:judgement,use_off_gcd=1,if=<range>:seal_of_command,focus=1

Decided · per-display setting

Sequences, display by display

Primary and AOE each have a "Sequences" setting on their options page; Cooldowns, Interrupts and Defensives never sequence (L1315). Where it is off, sequences do not exist for that display: the compiler makes no sequence keys for it, and its pass skips every sequence line, start lines included, as if they were not in the priority. The setting covers sequences only. The owner: "Yes freeform windows will still work".

Phased plan · final

Six phases, belief first

  1. Phase 0

    Docs

    Fix design §3a (the wowsims strict start at the pin is "first step ready") and name SimC as the default reference; record v6 as the build reference; this page; draft the release notes (windows reserved, displays showing abilities outside their category, the Sequences setting).
  2. Phase 1

    Belief

    APL rows by key, the operations buffer and WindowOp, Drain order, the four operations as writes, parking, reset_on_target_change for APL rows and Lua windows, step_timeout (4 s), RegisterWindow's checks, generation-bump apply, operation logging, counters.Gate: fast checks. Matrix runner and test kit built here; belief-only columns asserted first.
  3. Phase 2

    Core and compiler

    The reserved windows list, errors E1-E7, keys, sequence syntax with every option; lines as commands with the per-slot fired mark; the uniform line form; the restart with no cap and the restarts-per-slot count; the three start tests and the two ability fields; the hold; give-up, the strict skip and the three plain modes; the start-line bypass in Primary and AOE; the translator writing its flags; snapshot lines.CPU gate: shipped packs unchanged (none has a window line yet), plus three synthetic priorities (flapping pair, chain of three, held-true refresh) measured for CPU ratio and restarts per slot. A high number becomes a warning proposal, never a cap.
  4. Phase 3

    Three real-world tests

    Warrior Arms, strict: the new rule 14 against its prev.1 chains, also with Cooldowns separate. Nothing open

Risks, readings and notes for the builders

Every question is decided, and no contradiction is open. The two items v6 first raised here (Paladin move steps, the Arms start test) were ruled on and are the first two cards of the Decided list.

Readings v6 made

Small points the rulings imply but do not spell out, each the narrowest reading.

  • The Lua-window reset is the controller's reading of L837. Flipping it to APL-only means deleting one field.
  • A reset Lua window also forgets its evaluator's last value, so a still-true evaluator reopens it at step 1.
  • step_timeout= is for strict sequences only; a plain sequence has no deadline.
  • mode= together with wait_on_ready is an error, rather than one silently winning.
  • A plain sequence's generated lines all sit under its condition, so a false if= shows and skips nothing.
  • The start-line bypass applies in Primary and AOE only, as the ruling names them.
  • sequence_ready takes no arguments, like usable, and reaches the normal test as ready(); the ruling left the mechanism to the design. The fields also cover the any-member start test of allow_skip=1.
  • hha keeps Arcane Shot at its three list positions through ordinary lines that read window.hha.next.arcane_shot, so the pack's order does not change.

Not checked in code, for the builders

  • Phase 1: whether a second Drain can run before all five passes finish; whether the two GCD tests ever disagree; where a Lua window keeps its evaluator's last value.
  • Phase 2: whether a slot-1 line is always evaluated at delay 0; whether the core can ask "castable at the end of the GCD" for a member that is not the line being walked; how a line is accepted with a wait for mode=wait; every place the fired mark is cleared today; whether mode or step_timeout collide with an existing entry field.
  • Phase 2: whether the four gates can be skipped for one judgement without a second code path, and how ready() reaches the handler without an allocation.
  • Phase 3: that Overpower's gate is its form field and Rend's a nobuff field in the Warrior class file, and whether Fury needs the same; an APL expression for "before the first main-hand swing"; tests and tools that name hha, move1, move2 as class windows.
  • Phase 5: whether the Actions tab can show a list of steps without a new widget.

Risks

  • Flapping. Open and close conditions both true: the window opens and closes in every slot of every pass. By design; a cost and a surprise, not a fault.
  • A window that never closes. A held-true open reopens the moment the window expires; refresh=1 burns through max_refresh in under a second.
  • Restart cost, with no cap and in every slot. Worst case is window lines × slots extra walks per display per update. Bounded and fixed at compile time; Phase 2 measures it and the snapshot shows it.
  • Forecast slots differ from what is sent. With the per-slot mark the copy can open and close windows the belief never hears about. Slot 1's operations are what the belief received.
  • Replay determinism. Rests on the belief changing only in Drain, operations being writes, and the log holding them in order. The harness invariant is the guard.
  • The default skip is sharp. A member that is uncastable for one pass is dropped for the run. SimC's behaviour, and a known surprise there.
  • mode=wait can stall a display. A waited member that never becomes castable blocks everything below the line.
  • The default strict start cannot begin a sequence whose later member is enabled by its first unless the pack marks that ability with sequence_ignore or sequence_ready, or the line says start_on_first=1. An imported SimC line over unmarked abilities never starts.
  • A start test that looks past a gate can be wrong. If the first member does not lift the gate, the sequence opens and the give-up closes it: one wasted recommendation, repeated while the condition holds. The fields are pack code, not visible in the priority text.
  • Two families of behaviour. A translator pack and a hand-written line with the same members act differently, by design. The Actions tab and the snapshot show why.
  • Displays show abilities outside their category. A separated cooldown in Primary, as a later member and now as a first member. A cooldown that exists only as a sequence's first member does not show in Cooldowns, which never sequences.
  • The conversions move shipped behaviour. hha restarts its loop one update later than the Lua window; the Paladin opener depends on a close line and on every old .up read becoming "up and not done".
  • A press before the window is open: up to one update with the wowsims start, longer with the default start. Phase 3 counts both.
  • The latch repeats. An unpressed strict sequence is opened again after every step timeout.
  • A reserved list name. A user's old list called windows gets errors on load. Release note.

How a pack author sees it

No new option. Everything is in the existing debug output and snapshot, in plain names.

  • Each window line's debug text gains its outcome: opened and restarted, already open, already fired this slot, or forecast only.
  • A "Windows" section per display: "Sequences: on/off", state as seeded, the operations slot 1 sent in order with the line that sent each, and the restarts in each slot.
  • Each open sequence's effective options, every STEP with the member it dropped, and for mode=wait the member waited on.
  • Two rolling numbers per window: operations and opens in the last 10 s. A flapping window reads "burst: 100 operations / 10 s".
  • A belief section with the keys, operations applied and dropped since combat start.
  • Compile errors E1-E7 with the line number and the plain name.
